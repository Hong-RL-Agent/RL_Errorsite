# FitTrack 의도적 기능 오류 명세서 (BUGS.md)

본 문서는 FitTrack (D-03) 피트니스 운동 기록 웹사이트에 의도적으로 삽입된 5가지 기능 오류에 대한 명세서입니다.  
모든 오류의 검증 확인전략은 **ACTION_REPLAY**이며, 단일 사용자 행동(Trigger Action) 실행 전후의 UI, DOM, Network(API 페이로드), State(SQLite 데이터베이스)를 비교하여 결정적으로 재현 및 검증할 수 있습니다.

---

## 1. BUG-D03-01: 특정 근력 운동 완료 버튼 클릭 시 DB 미반영 오류

- **bug_id**: `BUG-D03-01`
- **오류명**: 특정 근력 운동(트라이셉스 푸시다운) 완료 버튼 클릭 시 완료 토글 알림은 표시되나 DB 상 완료 상태 미변경 오류
- **확인전략**: `ACTION_REPLAY`
- **대상 운동 기록**: 기록 ID `3` (`트라이셉스 푸시다운`, 2026-10-01 등록건, 초기 `is_completed: 0`)
- **UI 조작 위치**:
  - 운동 기록 카드 목록에서 `트라이셉스 푸시다운` (ID: 3) 카드의 하단 좌측 [완료 체크] 버튼 1회 클릭
- **Precondition (사전조건)**:
  - 시스템 초기 상태 (`POST /api/test/reset` 호출 완료).
  - 기록 ID `3`의 `is_completed` 값이 `0` (미완료)이어야 함.
- **Trigger (사용자 행동)**:
  - `트라이셉스 푸시다운` 카드의 [완료 체크] 버튼을 1회 클릭 (`PATCH /api/workouts/3/complete`).
- **정상 동작 (Expected Behavior)**:
  - 버튼이 [운동 완료]로 바뀌고, 백엔드 DB의 `is_completed`가 `1`로 업데이트되어야 함.
- **실제 오류 동작 (Actual Defect Behavior)**:
  - "운동 세션 완료 상태가 변경되었습니다" 성공 알림이 노출되지만, 백엔드 처리에서 `workoutId === 3`일 때 DB의 `is_completed` UPDATE 쿼리를 건너뛰고 `is_completed: 0`을 그대로 유지함.
  - API 재조회나 화면 새로고침 시 해당 운동이 다시 [미완료] 상태로 남아있음.
- **필요한 Evidence (증거 데이터)**:
  - **UI**: 버튼 클릭 후 알림 표시 vs 페이지 새로고침 시 다시 [완료 체크] 미완료 상태로 렌더링.
  - **Network**: `PATCH /api/workouts/3/complete` 응답 객체의 `data.is_completed`가 `0`.
  - **State**: SQLite `SELECT is_completed FROM workouts WHERE id = 3`의 결과가 여전히 `0`.
- **확인 방법 (Verification Steps)**:
  1. `POST /api/test/reset` 실행.
  2. `트라이셉스 푸시다운` 카드의 [완료 체크] 버튼 클릭.
  3. 성공 알림 확인 후, `GET /api/workouts` API를 호출하여 `id: 3`의 `is_completed`가 `0`인지 확인.
  4. 화면 새로고침 시 여전히 미완료 회색 테두리 상태인지 확인.

## 2. BUG-D03-02: 특정 운동 기록 삭제 시 성공 알림 후 DB 잔류 오류

- **bug_id**: `BUG-D03-02`
- **오류명**: 특정 운동 기록(스쿼트, ID: 7) 삭제 시 성공 알림 발생 후 재조회 시 그대로 나타나는 오류
- **확인전략**: `ACTION_REPLAY`
- **대상 운동 기록**: 기록 ID `7` (`스쿼트`, 2026-10-02 등록건, 3세트 10회 60kg)
- **UI 조작 위치**:
  - 운동 기록 카드 목록에서 `스쿼트` (ID: 7) 카드의 우측 하단 빨간색 휴지통([삭제]) 버튼 1회 클릭
- **Precondition (사전조건)**:
  - 시스템 초기 상태 (`POST /api/test/reset` 호출 완료).
  - 기록 목록에 ID `7` (`스쿼트`)가 존재해야 함.
- **Trigger (사용자 행동)**:
  - ID `7` (`스쿼트`) 카드의 [삭제] 버튼 1회 클릭 (`DELETE /api/workouts/7`).
- **Expected (정상 동작)**:
  - "운동 기록이 삭제되었습니다." 알림과 함께 목록 및 DB에서 완전히 삭제되어야 함.
- **Actual (실제 오류 동작)**:
  - 삭제 성공 알림이 발생하고 200 OK를 반환하지만, 백엔드에서 ID 7일 때 실제 `DELETE FROM workouts WHERE id = 7` 쿼리를 실행하지 않음.
  - 데이터 재조회(`GET /api/workouts`) 시 ID 7 레코드가 그대로 반환되어 목록에 다시 나타남.
- **필요한 Evidence (증거 데이터)**:
  - **UI**: 삭제 버튼 클릭 후 새로고침 또는 날짜 변경 후 재선택 시 `스쿼트` 카드가 그대로 표시됨.
  - **Network**: `DELETE /api/workouts/7` 호출 성공 후 `GET /api/workouts` 응답 배열에 `id: 7`이 여전히 포함됨.
  - **State**: SQLite `SELECT COUNT(*) FROM workouts WHERE id = 7` 결과가 `1`.
- **확인 방법 (Verification Steps)**:
  1. `POST /api/test/reset` 실행.
  2. ID `7` (`스쿼트`) 카드의 [삭제] 버튼 클릭.
  3. 상단 날짜 선택기에서 다른 날짜를 선택했다가 다시 오늘 날짜를 선택하거나 새로고침.
  4. ID `7` (`스쿼트`) 카드가 삭제되지 않고 그대로 유지되어 있음을 확인.

## 3. BUG-D03-03: 특정 운동 세트 수 변경 저장 시 다른 값 저장 오류

- **bug_id**: `BUG-D03-03`
- **오류명**: 특정 운동(데드리프트, ID: 11) 세트 수 변경 시 의도한 값과 다른 세트 수(3세트)로 저장되는 오류
- **확인전략**: `ACTION_REPLAY`
- **대상 운동 기록**: 기록 ID `11` (`데드리프트`, 2026-10-03 등록건, 초기 4세트)
- **UI 조작 위치**:
  1. ID `11` (`데드리프트`) 카드의 우측 하단 연필([수정]) 버튼 클릭
  2. 수정 모달에서 [세트 수] 입력값을 `5`로 변경
  3. 하단 [수정사항 저장] 버튼 클릭
- **Precondition (사전조건)**:
  - 시스템 초기 상태 (`POST /api/test/reset` 호출 완료).
  - 기록 ID `11`의 초기 세트 수는 `4SET`이어야 함.
- **Trigger (사용자 행동)**:
  - 세트 수를 `5`로 입력하고 [수정사항 저장] 1회 클릭 (`PATCH /api/workouts/11`).
- **Expected (정상 동작)**:
  - DB와 카드 화면에 세트 수가 `5SET`으로 변경 및 표시되어야 함.
- **Actual (실제 오류 동작)**:
  - 백엔드 처리 로직에서 ID 11 수정 시 세트 수를 강제로 `3`으로 덮어씌워 저장함.
  - 수정 완료 후 카드의 세트 수가 `5SET`이 아닌 `3SET`으로 표시됨.
- **필요한 Evidence (증거 데이터)**:
  - **UI**: 모달에 입력한 세트 수 `5` vs 저장 후 카드의 `3SET`.
  - **Network**: 요청 페이로드 `{ sets: 5 }` vs 응답 페이로드 `{ data: { sets: 3 } }`.
  - **State**: SQLite `SELECT sets FROM workouts WHERE id = 11` 결과가 `3`.
- **확인 방법 (Verification Steps)**:
  1. `POST /api/test/reset` 실행.
  2. ID `11` (`데드리프트`)의 수정 버튼 클릭 -> 세트 수를 `5`로 변경 후 저장.
  3. 목록에서 해당 카드의 세트 수가 `5SET`이 아닌 `3SET`으로 저장되었는지 확인.
  4. Network 탭에서 `PATCH /api/workouts/11`의 응답 객체 `sets` 값이 `3`인지 확인.

## 4. BUG-D03-04: 특정 운동 수정 시 다른 날짜의 운동 기록 변경 오류

- **bug_id**: `BUG-D03-04`
- **오류명**: 특정 날짜 운동(2026-10-04 숄더프레스, ID: 14) 수정 시 다른 날짜의 운동(2026-10-02 숄더프레스, ID: 8)이 변경되는 오류
- **확인전략**: `ACTION_REPLAY`
- **대상 운동 기록**:
  - 사용자 수정 대상: 기록 ID `14` (`오버헤드 숄더프레스`, 일자: `2026-10-04`, 4세트 8회 45kg)
  - 실제 변경 대상: 기록 ID `8` (`오버헤드 숄더프레스`, 일자: `2026-10-02`, 4세트 10회 40kg)
- **UI 조작 위치**:
  1. 기록 ID `14` (`2026-10-04`의 `오버헤드 숄더프레스`) 카드의 [수정] 버튼 클릭
  2. [중량(kg)]을 `55`로, [메모]를 `새로운 중량 PR 달성`으로 입력
  3. [수정사항 저장] 클릭
- **Precondition (사전조건)**:
  - 시스템 초기 상태 (`POST /api/test/reset` 호출 완료).
  - ID 14는 45kg (2026-10-04), ID 8은 40kg (2026-10-02)이어야 함.
- **Trigger (사용자 행동)**:
  - ID 14의 수정 모달에서 중량을 55kg로 변경하고 [수정사항 저장] 1회 클릭 (`PATCH /api/workouts/14`).
- **Expected (정상 동작)**:
  - 2026-10-04의 ID 14 카드가 55kg로 변경되고, 2026-10-02의 ID 8 카드는 40kg로 유지되어야 함.
- **Actual (실제 오류 동작)**:
  - 수정한 2026-10-04의 ID 14는 45kg 그대로 유지됨.
  - 대신 다른 날짜(2026-10-02)에 등록된 ID 8 숄더프레스의 중량이 55kg로 엉뚱하게 변경됨.
- **필요한 Evidence (증거 데이터)**:
  - **UI**: ID 14 카드의 중량은 여전히 45kg이고, ID 8 카드의 중량이 55kg로 바뀐 화면.
  - **Network**: `PATCH /api/workouts/14` 전송 후 `GET /api/workouts` 조회 시 ID 8의 `weight_kg`가 55로 변경된 데이터.
  - **State**: SQLite `SELECT id, weight_kg FROM workouts WHERE id IN (8, 14)`에서 ID 8만 55kg로 업데이트됨.
- **확인 방법 (Verification Steps)**:
  1. `POST /api/test/reset` 실행.
  2. ID 14 (`2026-10-04` 숄더프레스)의 수정 버튼 클릭 -> 중량을 55kg로 변경 후 저장.
  3. ID 14 카드의 중량이 여전히 45kg인지 확인.
  4. ID 8 (`2026-10-02` 숄더프레스) 카드를 확인하여 중량이 55kg로 변경되었는지 확인.

## 5. BUG-D03-05: 특정 운동 목표 달성 체크 시 달성률 계산 왜곡 오류

- **bug_id**: `BUG-D03-05`
- **오류명**: '주 5회 근력운동 달성' 목표 체크 클릭 시 목표 달성률이 실제 값과 다르게 왜곡 계산되는 오류
- **확인전략**: `ACTION_REPLAY`
- **대상 목표**: 주간 목표 ID `1` (`주 5회 근력운동 달성`, 목표: 5회, 초기 달성치: 4회, 초기 달성률: 80%)
- **UI 조작 위치**:
  - [주간 트레이닝 목표 달성률] 섹션에서 `주 5회 근력운동 달성` 목표 앞의 체크 원형 버튼 1회 클릭
- **Precondition (사전조건)**:
  - 시스템 초기 상태 (`POST /api/test/reset` 호출 완료).
  - 목표 ID 1의 초기 상태: 4 / 5 회 (80%).
- **Trigger (사용자 행동)**:
  - 목표 ID 1의 달성 체크 버튼 1회 클릭 (`PATCH /api/goals/1/check`).
- **Expected (정상 동작)**:
  - 목표가 완료됨에 따라 5 / 5 회 (100%)로 달성 완료 처리되어야 함.
- **Actual (실제 오류 동작)**:
  - 백엔드 목표 토글 핸들러에서 목표 ID 1의 달성치를 정상 완료값(5) 대신 `1`로 왜곡 저장함.
  - 목표 달성률이 100%가 아니라 `1 / 5 회 (20%)`로 급락하여 게이지가 줄어드는 오류 발생.
- **필요한 Evidence (증거 데이터)**:
  - **UI**: 체크 클릭 후 `5 / 5 회 (100%)`가 아닌 `1 / 5 회 (20%)`로 표시되는 게이지 바.
  - **Network**: `PATCH /api/goals/1/check` 응답 데이터의 `data.current_value`가 `1`.
  - **State**: SQLite `SELECT current_value FROM goals WHERE id = 1` 결과가 `1`.
- **확인 방법 (Verification Steps)**:
  1. `POST /api/test/reset` 실행.
  2. `주 5회 근력운동 달성` 목표 상태 확인: `4 / 5 회 (80%)`.
  3. 해당 목표의 체크 버튼 1회 클릭.
  4. 목표 텍스트 및 게이지 확인: `1 / 5 회 (20%)`로 왜곡되어 표시되는지 검증.
