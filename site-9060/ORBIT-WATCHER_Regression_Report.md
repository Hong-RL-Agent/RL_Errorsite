# ORBIT-WATCHER: System Regression & Anti-Pattern Analysis Report

**Target Environment:** AI Simulation Sandbox (PPO Agent Training)
**Theme:** "Cosmic Command" Space Debris Tracking

This report details the architectural anti-patterns, logical flaws, and resource exhaustion vulnerabilities simulated in the ORBIT-WATCHER training environment. This documentation serves as a guide for understanding how such flaws manifest in real-world systems and how AI agents can detect and mitigate them.

## 1. Implemented Logical Defect Models

### 1.1 Service Worker Navigation Preload Conflict
**Mechanism:** The Service Worker (`sw.js`) enables `navigationPreload`, but intentionally delays the resolution of the `fetch` event when navigating. This simulates a race condition or queue congestion where the preload response is available, but improper async handling causes the browser to stall before falling back to the network.
**Detection Signature:** Abnormally high Time To First Byte (TTFB) on navigation requests despite cached assets.

### 1.2 Sensitive Data Browser Cache Exposure
**Mechanism:** The `/api/telemetry/sensitive` endpoint serves high-risk classification data but intentionally omits `Cache-Control: no-store, no-cache` headers.
**Detection Signature:** The browser caches the GET request, and subsequent reloads or local inspections reveal sensitive telemetry data in the disk cache, violating security standards for classified data.

### 1.3 Cascading Tail Latency Amplification
**Mechanism:** The `/api/debris/scan` endpoint simulates a microservice architecture where a single request depends on multiple downstream services. By introducing arbitrary `Thread.sleep()` delays sequentially, a minor network jitter is amplified into a massive tail latency.
**Detection Signature:** High P99 response times on specific endpoints, disconnected from CPU or memory load, indicating blocking I/O or downstream synchronous waits.

## 2. Theoretical Analysis of Exhaustion Anti-Patterns

The following bottlenecks represent severe system/kernel-level defects. Due to their destructive nature, they are documented here for theoretical analysis rather than active execution.

### 2.1 Context Switching Storm (Thread Bomb)
**Theory:** Creating hundreds or thousands of concurrent worker threads for data tracking causes the OS scheduler to spend more CPU cycles context-switching between threads than executing actual logic.
**Metrics:** High CPU `sys` time, elevated `cs` (context switches) per second in `vmstat`, and low actual application throughput.

### 2.2 GC Stop-the-World Congestion
**Theory:** Continuously allocating large objects (e.g., massive arrays representing telemetry data) in Java without releasing them fast enough forces the Garbage Collector into frequent "Stop-The-World" pauses.
**Metrics:** High GC pause times, jagged memory usage graphs (sawtooth pattern but with high baseline), and intermittent request timeouts.

### 2.3 Disk I/O IOPS Exhaustion
**Theory:** A logging system that synchronously writes tens of thousands of meaningless trace logs per second to an SSD.
**Metrics:** 100% disk utilization (`iostat -x`), high `await` times, and thread blocking on file system sync operations.

### 2.4 Native Addon Off-Heap Leak
**Theory:** Using JNI or `ByteBuffer.allocateDirect` to allocate native, off-heap memory but failing to free it. Since this bypasses the JVM GC, the process consumes RAM until the OS OOM Killer terminates it.
**Metrics:** The process RSS (Resident Set Size) grows linearly over time while JVM heap usage remains stable and low.

### 2.5 File System Inode Exhaustion
**Theory:** Creating millions of empty temporary files (e.g., for caching orbit paths) consumes all available Inodes on the ext4 file system.
**Metrics:** Disk space shows plenty of availability (`df -h`), but `df -i` shows 100% Inode usage, preventing the creation of any new files or sockets.

### 2.6 SSD Write Amplification & I/O Latency
**Theory:** Repeatedly updating small fragments of data in a large file forces the SSD controller into continuous Read-Modify-Write cycles, accelerating wear and latency.
**Metrics:** High write latency, disk write MB/s significantly higher than application-level requested writes.

### 2.7 GPU Memory Fragmentation
**Theory:** The WebGL/Canvas frontend irregularly allocates and deallocates textures of random sizes, fragmenting VRAM.
**Metrics:** Browser memory bloat, dropping FPS over time, and eventual WebGL context loss errors due to inability to find contiguous VRAM blocks.

### 2.8 Network Softirq Imbalance
**Theory:** Configuring the container or OS to process all incoming network packet interrupts on a single CPU core (Core 0), while other cores remain idle.
**Metrics:** `top` shows Core 0 at 100% `si` (software interrupt) load, while other cores are idle. Packet drops occur despite overall CPU availability.
