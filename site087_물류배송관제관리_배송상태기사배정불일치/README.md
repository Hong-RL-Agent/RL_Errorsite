## 📋 정상 기능 요약

- **전국 물류 관제 모니터링**: 6개 물류센터(서울, 경기, 중부, 영남, 호남, 제주)의 실시간 처리량 및 SVG 지도 관제.
- **배송 주문 및 기사 관제**: 35개 이상의 배송 주문 상태 추적 및 18명 기사별 할당 작업량 모니터링.
- **통합 이력 로그 & CS 문의**: 60개 이상의 배송 상태 변경 로그 및 20개 이상의 1:1 고객 문의 답변 관리.
- **기사 재배정 & 주소 변경**: 담당 배송 기사 모달 변경 및 배송지 정보 수정.

## ⚠️ 의도적으로 삽입된 8가지 복합 오류 목록

1. **Frontend 상태 + Backend 요청 순서 충돌**
   - **설명**: 배송 상태를 변경(3초 지연 완료)한 직후 담당 기사를 변경(0.1초 완료)하면, 기사 변경 API는 먼저 성공하지만 3초 뒤 완료되는 상태 변경 API 내부에 이전 기사 정보(`driverId`, `driverName`)가 동봉 저장되어 새로고침 시 새 배송 상태와 이전 기사 조합이 저장됩니다.

2. **Backend + JSON DB 상태 충돌**
   - **설명**: 배송 취소 API(0.5초 완료)를 호출한 직후 기사 재배정 API를 호출(4초 지연 완료)하면, 취소 요청은 먼저 성공하지만 늦게 완료된 재배정 요청이 취소된 배송을 다시 'IN_DELIVERY'(배송중) 상태로 재활성화시킵니다. 배송 목록에서는 취소됨, 기사 작업 보드에서는 배송중으로 불일치하게 됩니다.

3. **Frontend 정렬 인덱스 오류**
   - **설명**: 배송 목록을 지연시간순/배송비순으로 정렬한 뒤 상세 버튼을 누르면 상단 제목은 클릭한 운송장 번호로 표시되나 상세 패널의 고객명과 주소는 원본 정렬 전 배열의 다른 배송 데이터가 노출됩니다.

4. **통계 집계 불일치**
   - **설명**: 배송 완료 로그를 삭제(`DELETE /api/logs/:id`) 처리하여 이력 대장에서 소거하더라도, 대시보드의 완료 배송 수(`completedOrdersCount`)와 물류센터별 처리량 그래프 수치에는 차감되지 않고 계속 유지됩니다.

5. **Network stale response 오류**
   - **설명**: 물류센터 필터('CTR-01' 3초 지연 ➔ 'CTR-02' 0.2초 완료)와 배송 상태 필터를 빠르게 변경 시 오래된 응답이 최신 목록을 덮어써 중앙 배송 목록은 오래된 필터 결과, 오른쪽 요약 패널은 최신 필터 기준 데이터로 서로 불일치합니다.

6. **Session + Cache 잔존 오류**
   - **설명**: 관리자 A가 기사 배정 화면을 본 뒤 관리자 B로 로그인하면 배송 목록은 B 권한 기준으로 바뀌지만, 상단 지연 배송 개수 및 최근 배정 기사 캐시(`cachedDelayedCount`, `cachedRecentDriver`)는 A 데이터가 남아 노출됩니다.

7. **Backend 권한 로그 오류**
   - **설명**: 권한 없는 직원(role !== 'ADMIN')이 배송 상태 변경 API(`PATCH /api/orders/:id/status`)를 호출하면 HTTP 403을 반환하지만, 서버 내부 활동 로그에는 '상태 변경 성공 (ORDER STATUS UPDATE SUCCESS - 200 OK)'으로 잘못 기록됩니다.

8. **부분 저장 오류**
   - **설명**: 배송 주소 수정 모달/패널에서 우편번호, 상세주소, 배송메모를 한 번에 수정하면 백엔드 data.json에는 우편번호와 배송메모만 저장되고 상세주소는 이전 값을 유지하지만, 프론트엔드는 세 값이 모두 수정 성공한 것처럼 토스트 알림을 표시합니다.

## 🧪 테스트 시나리오

1. **Error 1 테스트**: 우측 패널에서 상태 선택 후 `상태 변경` 클릭 직후 담당 기사 선택 변경 ➔ 3초 후 새로고침 시 상태는 바뀌었으나 담당 기사는 이전 기사로 롤백됨을 확인.
2. **Error 2 테스트**: 우측 패널에서 `⚡ 배송 취소 후 기사 재배정` 클릭 ➔ 0.5초 후 취소 응답 ➔ 4초 후 재배정 응답이 완료되며 배송 목록(취소됨)과 기사 작업 보드(배송중) 간 상태 불일치 확인.
3. **Error 3 테스트**: 좌측 사이드바에서 `지연시간순` 정렬 선택 ➔ 상단 배송건의 상세보기 클릭 ➔ UI 상단 운송장 번호와 상세 패널의 고객명/주소가 상이함을 확인.
4. **Error 4 테스트**: 중앙 이력 대장에서 `🗑️ 삭제` 클릭 ➔ 대장에서는 삭제되나 대시보드 완료 건수 및 센터 처리량 그래프 수치가 유지됨을 확인.
5. **Error 5 테스트**: 좌측 센터 필터를 `서울 중앙 센터` 선택 직후 `경기 허브 터미널` 선택 ➔ 3초 후 늦은 이전 결과가 최신 목록을 덮어씀을 확인.
6. **Error 6 테스트**: 상단 로그인 사용자를 `김관제 팀장`에서 `이물류 실장`으로 전환 ➔ 배송 목록은 B로 바뀌나 상단 KPI 지연 배송 개수는 A 데이터로 잔존함을 확인.
7. **Error 7 테스트**: 상단 계정을 `정배송 사원 (일반 직원)`으로 전환 후 `🔒 일반 직원의 배송 상태 변경 시도` 클릭 ➔ UI/API는 HTTP 403 오류 반환 ➔ 백엔드 콘솔 로그에는 SUCCESS (200 OK)로 잘못 작성됨을 확인.
8. **Error 8 테스트**: 우측 하단 주소 수정 패널에서 상세주소 포함 입력 후 `주소 수정 저장` 클릭 ➔ 토스트는 성공으로 표시되나 새로고침 시 상세주소만 수정되지 않았음을 확인.
