## 📋 정상 기능 요약

- **대학교 기숙사 재적 학생 대장**: 45명 학생 명단, 학과, 성적 GPA, 배정 호실, 희망 룸메이트 및 입사 상태 관제.
- **기숙사 층별 호실 배치도 Grid**: 60개 호실(명덕관, 진리관, 봉사관 층별 2인실/1인실) 수용 인원 및 점유율 관리.
- **입사 신청 대장 & 사감 점검 로그**: 40건의 선발 신청(신청, 승인, 반려) 및 80건의 배정/점검/퇴사 감사 로그 관리.
- **생활관 권한 관리**: 생활관 관장(MANAGER)/사감원(STAFF) 권한 및 스마트키 도어락 발급 관제.

## ⚠️ 의도적으로 삽입된 8가지 복합 오류 목록

1. **Frontend + Backend 요청 순서 충돌**
   - **설명**: 학생의 호실을 변경(3초 지연 완료)한 직후 입사 상태를 '입사완료'(CHECKED_IN)로 변경(0.1초 완료)하면, 입사 상태 변경 API는 먼저 완료되나 3초 뒤 완료되는 호실 변경 API가 요청 시작 시점의 구 DB 스냅샷(이전 호실)을 덮어써 저장하여 새로고침 시 학생 상세의 호실과 호실 배치도의 학생 위치가 서로 달라집니다.

2. **Backend + JSON DB 상태 충돌**
   - **설명**: 퇴사 처리 API(0.5초 완료)를 호출한 직후 호실 점유 상태 갱신 API를 호출(4초 지연 완료)하면, 퇴사 처리는 성공하지만 늦게 완료된 점유 상태 갱신 요청이 퇴사 학생을 다시 CHECKED_IN 입사중 상태로 복원시킵니다. 학생 목록에서는 퇴사, 호실 배치도에서는 입사중 학생으로 표시됩니다.

3. **Frontend 정렬 인덱스 오류**
   - **설명**: 입사 신청 목록을 성적순/신청일순으로 정렬한 뒤 승인 버튼을 누르면 UI 알림은 클릭한 학생명으로 뜨지만, 백엔드 저장 데이터는 정렬 전 원본 배열의 다른 학생 ID에 연결되는 결함입니다.

4. **통계 집계 불일치**
   - **설명**: 호실 배정 로그를 삭제(`DELETE /api/allocation-logs/:id`) 처리하여 로그 목록에서 소거하더라도, 층별 점유율(`dormStats.occupancyRate`), 성별 배정 통계, 대기자 수 통계 수치에는 차감되지 않고 계속 잔존합니다.

5. **Network stale response 오류**
   - **설명**: 기숙사동 필터('명덕관' 3초 지연 ➔ '진리관' 0.2초 완료)와 입사 상태 필터를 빠르게 변경 시 오래된 응답(명덕관)이 최신 학생 목록을 덮어써 학생 목록은 오래된 필터 결과, 오른쪽 호실 요약은 최신 필터 기준 수치로 서로 불일치합니다.

6. **Session + Cache 잔존 오류**
   - **설명**: 직원 A가 학생 상세를 본 뒤 직원 B로 로그인하면 학생 목록은 B 권한 기준으로 바뀌지만, 상단 대기자 수 및 최근 학생 상세 캐시(`cachedWaitingApplicants`, `cachedRecentStudent`)는 A 데이터가 남아 노출됩니다.

7. **Backend 권한 로그 오류**
   - **설명**: 권한 없는 직원(role !== 'MANAGER')이 호실 강제 변경 API(`POST /api/rooms/:id/force-change-unauthorized`)를 호출하면 HTTP 403을 반환하지만, 서버 내부 활동 로그에는 '호실 강제 변경 성공 (ROOM FORCED CHANGE COMPLETED SUCCESSFULLY - 200 OK)'으로 잘못 기록됩니다.

8. **부분 저장 오류**
   - **설명**: 학생 정보 수정 모달/패널에서 연락처, 보호자 연락처, 희망 룸메이트를 동시에 수정하면 백엔드 data.json에는 연락처와 희망 룸메이트만 저장되고 보호자 연락처는 이전 값을 유지하지만, 프론트엔드는 세 항목 모두 수정 성공한 것으로 표시합니다.

## 🧪 테스트 시나리오

1. **Error 1 테스트**: 우측 관제 패널에서 배정 호실 변경 선택 후 `호실 변경 후 즉시 입사 상태 변경 (Error 1)` 클릭 ➔ 0.1초 후 입사 상태 변경 응답 ➔ 3초 후 호실 변경 응답 완료 ➔ 새로고침 시 이전 호실로 롤백 저장됨을 확인.
2. **Error 2 테스트**: 우측 관제 패널에서 `⚡ 퇴사 처리 후 호실 점유 갱신 연쇄 실행 (Error 2)` 클릭 ➔ 0.5초 후 퇴사 응답 ➔ 4초 후 점유 갱신 응답 완료 ➔ 퇴사한 학생이 CHECKED_IN 입사중 상태로 복원됨을 확인.
3. **Error 3 테스트**: 좌측 사이드바에서 `성적 GPA 높은순` 정렬 선택 ➔ 최상단 신청의 `승인` 클릭 ➔ UI 상단 학생명과 우측 관제 패널의 승인 학생 정보가 상이함을 확인.
4. **Error 4 테스트**: 중앙 감사 로그 대장에서 `🗑️ 로그 삭제` 클릭 ➔ 대장에서는 삭제되나 대시보드 점유율 수치가 유지됨을 확인.
5. **Error 5 테스트**: 좌측 기숙사동 필터를 `명덕관` 선택 직후 `진리관` 선택 ➔ 3초 후 늦은 이전 명덕관 결과가 최신 진리관 학생 목록을 덮어씀을 확인.
6. **Error 6 테스트**: 상단 로그인 사감을 `김행정 관장`에서 `이호실 사감`으로 전환 ➔ 학생 목록은 B로 바뀌나 상단 KPI 대기자 건수는 A 데이터로 잔존함을 확인.
7. **Error 7 테스트**: 상단 계정을 일반 스태프 사감으로 테스트 시 `🔒 권한 없는 일반 직원의 호실 강제 변경 시도` 클릭 ➔ UI/API는 HTTP 403 오류 반환 ➔ 백엔드 콘솔 로그에는 SUCCESS (200 OK)로 잘못 작성됨을 확인.
8. **Error 8 테스트**: 우측 하단 학생 정보 수정 패널에서 보호자 연락처 포함 입력 후 `학생 정보 저장` 클릭 ➔ 토스트는 성공으로 표시되나 새로고침 시 보호자 연락처만 수정되지 않았음을 확인.
