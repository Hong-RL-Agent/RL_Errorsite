# PennyLog 의도적 기능 오류 명세서 (BUGS.md)

본 문서는 PennyLog (D-02) 개인 가계부 및 자산 관리 웹사이트에 의도적으로 삽입된 5가지 기능 오류에 대한 명세서입니다.  
모든 오류의 검증 확인전략은 **ACTION_REPLAY**이며, 단일 행동(Trigger Action) 실행 전후의 UI, Network(API 응답), State(데이터베이스 상태)를 비교하여 결정적으로 재현 및 검증할 수 있습니다.

---

## 1. BUG-D02-01: 특정 카테고리 지출 추가 시 금액 불일치 저장 오류

- **bug_id**: `BUG-D02-01`
- **오류명**: '교육/자기계발' 카테고리 지출 등록 시 입력한 금액과 다른 금액(+10,000원)으로 저장되는 오류
- **확인전략**: `ACTION_REPLAY`
- **대상 카테고리**: `교육/자기계발` (category_id: `6`)
- **UI 클릭 및 조작 위치**:
  1. 우측 상단 [거래 내역 추가] 버튼 클릭
  2. 유형 선택: [지출] 선택
  3. 거래명 입력: `온라인 코딩 테스트 강의 결제`
  4. 금액 입력: `50000` (50,000원)
  5. 카테고리 선택: `교육/자기계발`
  6. 결제 계좌 선택: `토스뱅크 주거래계좌`
  7. [거래 등록 완료] 버튼 클릭
- **Precondition (사전조건)**:
  - 시스템 초기 상태 (`POST /api/test/reset` 호출 완료).
- **Trigger (사용자 행동)**:
  - '교육/자기계발' 카테고리로 금액 `50000`원을 입력하고 [거래 등록 완료] 1회 클릭 (`POST /api/transactions`).
- **Expected (정상 동작)**:
  - 거래 목록 및 DB에 입력 금액인 `50,000원`으로 저장되고, 지출 금액이 정확히 50,000원으로 표시되어야 함.
- **Actual (실제 오류 동작)**:
  - 백엔드 처리 로직에서 카테고리 ID가 6인 경우 금액에 10,000원이 자동 가산되어 DB에 `60,000원`으로 저장됨.
  - 거래 내역 테이블에 `60,000원`으로 등록되어 표시됨.
- **필요한 Evidence (증거 데이터)**:
  - **UI**: 입력창의 `50,000` vs 등록 후 테이블 행의 `-60,000원`.
  - **Network**: 요청 페이로드 `{ amount: 50000, category_id: 6 }` vs 응답 페이로드 `{ data: { amount: 60000 } }`.
  - **State**: SQLite `SELECT amount FROM transactions WHERE title = '온라인 코딩 테스트 강의 결제'` 결과가 `60000`.
- **확인 방법 (Verification Steps)**:
  1. `POST /api/test/reset` 실행.
  2. UI에서 '교육/자기계발' 카테고리로 50,000원 지출 등록.
  3. 거래 목록 상단에 새로 등록된 행의 금액이 `50,000원`이 아닌 `60,000원`으로 표시되는지 확인.
  4. 개발자 도구 Network 탭에서 `POST /api/transactions` 응답 객체의 `amount` 필드가 `60000`인지 확인.

## 2. BUG-D02-02: 특정 거래 삭제 시 성공 알림 후 대상 잔류 오류

- **bug_id**: `BUG-D02-02`
- **오류명**: 특정 거래(스타벅스 커피 쿠폰 구매, ID: 15) 삭제 시 성공 알림 후에도 삭제 대상이 그대로 남아있는 오류
- **확인전략**: `ACTION_REPLAY`
- **대상 거래**: 거래 ID `15` (`스타벅스 커피 쿠폰 구매`, 9,900원, 2026-10-05)
- **UI 클릭 위치**:
  - 상세 거래 내역 테이블에서 일자 `2026-10-05`, 거래명 `스타벅스 커피 쿠폰 구매` 행 우측의 빨간색 휴지통([삭제]) 버튼 1회 클릭
- **Precondition (사전조건)**:
  - 시스템 초기 상태 (`POST /api/test/reset` 호출 완료).
  - 거래 목록에 ID `15` (`스타벅스 커피 쿠폰 구매`)가 존재해야 함.
- **Trigger (사용자 행동)**:
  - 거래 ID `15`의 [삭제] 버튼 1회 클릭 (`DELETE /api/transactions/15`).
- **Expected (정상 동작)**:
  - "거래 내역이 성공적으로 삭제되었습니다." 토스트와 함께 목록 및 DB에서 해당 거래가 즉시 제거되어야 함.
- **Actual (실제 오류 동작)**:
  - 삭제 성공 토스트("거래 내역이 성공적으로 삭제되었습니다.")가 정상 노출되고 200 OK가 반환되지만, 백엔드에서 ID 15일 때 실제 DELETE 쿼리를 건너뜀.
  - 화면 갱신 후에도 `스타벅스 커피 쿠폰 구매` 행이 목록에 그대로 남아있음.
- **필요한 Evidence (증거 데이터)**:
  - **UI**: 삭제 버튼 클릭 후에도 테이블에 여전히 `스타벅스 커피 쿠폰 구매` 행이 존재하는 화면.
  - **Network**: `DELETE /api/transactions/15` 200 OK 성공 응답 확인.
  - **State**: `GET /api/transactions` 재조회 결과에 `id: 15` 레코드가 계속 포함되어 있음.
- **확인 방법 (Verification Steps)**:
  1. `POST /api/test/reset` 실행.
  2. 테이블에서 `스타벅스 커피 쿠폰 구매` 확인.
  3. 해당 행의 휴지통([삭제]) 버튼 클릭.
  4. "삭제되었습니다" 토스트 확인 후 테이블 목록 확인 -> `스타벅스 커피 쿠폰 구매`가 삭제되지 않고 그대로 유지됨을 검증.

## 3. BUG-D02-03: 특정 거래 카테고리 수정 시 타 거래 변경 오류

- **bug_id**: `BUG-D02-03`
- **오류명**: 특정 거래(교보문고 도서 구매, ID: 8) 카테고리 변경 시 다른 거래(올리브영 생필품 구매, ID: 7)의 카테고리가 변경되는 오류
- **확인전략**: `ACTION_REPLAY`
- **대상 거래**:
  - 사용자 수정 대상: 거래 ID `8` (`교보문고 도서 구매`, 현재 카테고리: `교육/자기계발`)
  - 실제 변경 대상: 거래 ID `7` (`올리브영 생필품 구매`, 현재 카테고리: `생활/마트`)
- **UI 클릭 위치**:
  1. 거래 내역 테이블에서 `교보문고 도서 구매` (ID: 8) 행 우측의 연필([수정]) 버튼 클릭
  2. 모달 내 [카테고리 변경] 드롭다운에서 `문화/여가` (category_id: 8) 선택
  3. 하단 [수정사항 저장] 버튼 클릭
- **Precondition (사전조건)**:
  - 시스템 초기 상태 (`POST /api/test/reset` 호출 완료).
  - ID 8의 카테고리는 `교육/자기계발`, ID 7의 카테고리는 `생활/마트`이어야 함.
- **Trigger (사용자 행동)**:
  - ID 8의 수정 모달에서 카테고리를 `문화/여가`로 선택 후 [수정사항 저장] 클릭 (`PATCH /api/transactions/8`).
- **Expected (정상 동작)**:
  - `교보문고 도서 구매`의 카테고리가 `문화/여가`로 변경되고, `올리브영 생필품 구매`는 기존 `생활/마트`를 유지해야 함.
- **Actual (실제 오류 동작)**:
  - `교보문고 도서 구매`의 카테고리는 변경되지 않고 기존 `교육/자기계발`로 그대로 유지됨.
  - 대신 직전 거래인 `올리브영 생필품 구매` (ID: 7)의 카테고리가 `문화/여가`로 엉뚱하게 변경됨.
- **필요한 Evidence (증거 데이터)**:
  - **UI**: 수정 후 테이블에서 ID 8은 여전히 `교육/자기계발`이고, ID 7이 `문화/여가`로 변경된 화면.
  - **Network**: `PATCH /api/transactions/8` 호출 후 `GET /api/transactions`에서 ID 7의 `category_name`이 `"문화/여가"`로 바뀐 데이터.
- **확인 방법 (Verification Steps)**:
  1. `POST /api/test/reset` 실행.
  2. `교보문고 도서 구매`의 수정 버튼 클릭 -> 카테고리를 `문화/여가`로 변경 후 저장.
  3. 목록에서 `교보문고 도서 구매`의 카테고리 확인 (여전히 `교육/자기계발`).
  4. 바로 위의 `올리브영 생필품 구매` 카테고리 확인 (`문화/여가`로 변경되어 있음).

## 4. BUG-D02-04: 특정 수입 거래 등록 시 지출 합계 오반영 오류

- **bug_id**: `BUG-D02-04`
- **오류명**: '부수입/보너스' 카테고리 수입 거래 등록 시 수입 합계 대신 지출 합계에 가산되는 오류
- **확인전략**: `ACTION_REPLAY`
- **대상 카테고리**: `부수입/보너스` (category_id: `11`)
- **UI 클릭 위치**:
  1. 우측 상단 [거래 내역 추가] 버튼 클릭
  2. 유형 선택: [수입] 버튼 클릭
  3. 거래명 입력: `블로그 원고료 입금`
  4. 금액 입력: `150000` (150,000원)
  5. 카테고리 선택: `부수입/보너스`
  6. 결제 계좌 선택: `토스뱅크 주거래계좌`
  7. [거래 등록 완료] 버튼 클릭
- **Precondition (사전조건)**:
  - 시스템 초기 상태 (`POST /api/test/reset` 호출 완료).
  - 초기 상태: 이번 달 총 수입 4,278,500원 / 총 지출 895,350원 (2026-10월 기준).
- **Trigger (사용자 행동)**:
  - '부수입/보너스' 카테고리로 150,000원 수입 등록 1회 클릭 (`POST /api/transactions`).
- **Expected (정상 동작)**:
  - 상단 KPI 카드의 [이번 달 총 수입]이 150,000원 증가 (4,278,500원 -> 4,428,500원)해야 하며, [이번 달 총 지출]은 변동 없어야 함.
- **Actual (실제 오류 동작)**:
  - 등록된 거래의 유형은 '수입'으로 표기되지만, 월별 통계 집계(`GET /api/stats/monthly`)에서 수입 합계 대신 [이번 달 총 지출]에 150,000원이 가산됨.
  - 지출 합계가 895,350원 -> 1,045,350원으로 증가하고, 수입 합계는 그대로 유지됨.
- **필요한 Evidence (증거 데이터)**:
  - **UI**: 상단 카드 [이번 달 총 수입] 불변 vs [이번 달 총 지출] 150,000원 급증.
  - **Network**: `GET /api/stats/monthly` 응답의 `total_income`은 불변이고 `total_expense`가 150,000원 증가한 JSON 데이터.
- **확인 방법 (Verification Steps)**:
  1. `POST /api/test/reset` 실행.
  2. 상단 카드의 [이번 달 총 수입]과 [이번 달 총 지출] 금액 기록.
  3. [거래 내역 추가] -> [수입] -> `부수입/보너스` 카테고리로 150,000원 등록.
  4. 상단 카드 확인: 수입은 그대로이고, 지출 금액이 150,000원 증가했음을 확인.

## 5. BUG-D02-05: 특정 예산 수정 시 프론트엔드 기존 금액 표시 유지 오류

- **bug_id**: `BUG-D02-05`
- **오류명**: '식비' 카테고리 예산 수정 시 백엔드 저장은 성공하나 프론트엔드 UI에 기존 금액(500,000원)이 계속 표시되는 오류
- **확인전략**: `ACTION_REPLAY`
- **대상 예산**: `식비` (category_id: `1`, budget ID: `1`, 초기 예산: 500,000원)
- **UI 클릭 위치**:
  1. [월별 카테고리 예산 진행률] 섹션에서 `식비` 행 우측의 연필([수정]) 버튼 클릭
  2. 모달 내 [목표 월 예산 한도] 입력창에 `700000` (700,000원) 입력
  3. [예산 변경 적용] 버튼 클릭
- **Precondition (사전조건)**:
  - 시스템 초기 상태 (`POST /api/test/reset` 호출 완료).
  - '식비'의 표시 예산이 `500,000원`이어야 함.
- **Trigger (사용자 행동)**:
  - '식비' 예산을 700,000원으로 변경 후 [예산 변경 적용] 1회 클릭 (`PATCH /api/budgets/1`).
- **Expected (정상 동작)**:
  - "목표 예산이 성공적으로 변경되었습니다." 토스트와 함께 화면의 식비 목표 예산이 `700,000원`으로 갱신되고 진행률(%)도 재계산되어야 함.
- **Actual (실제 오류 동작)**:
  - 백엔드 DB에는 `monthly_budget = 700000`으로 정상 업데이트되지만, 프론트엔드 UI 렌더링에서 식비 항목의 목표 예산 금액이 여전히 기존 금액인 `500,000원`으로 고정 노출됨.
- **필요한 Evidence (증거 데이터)**:
  - **UI**: 모달 저장 후에도 예산 행에 `500,000원`으로 표시되는 화면.
  - **Network**: `PATCH /api/budgets/1` 성공 응답 및 `GET /api/budgets` 응답 상 `monthly_budget: 700000`으로 반환되는 백엔드 데이터와 UI의 불일치.
- **확인 방법 (Verification Steps)**:
  1. `POST /api/test/reset` 실행.
  2. '식비' 예산의 연필 버튼 클릭 -> 700,000원으로 변경 후 [예산 변경 적용] 클릭.
  3. 성공 알림 확인 후 화면의 '식비' 목표 예산 확인 -> 여전히 `500,000원`으로 표시됨을 검증.
  4. Network 탭에서 `GET /api/budgets`를 확인하여 백엔드에는 `700000`으로 정상 저장되어 있음을 대조 검증.
