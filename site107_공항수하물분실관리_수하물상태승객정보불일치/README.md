## 📋 정상 기능 요약

- **공항 실시간 수하물 관제 대장**: 55개 수하물 바코드 태그, 위치, 중량(kg), 담당 핸들러 및 추적 관제.
- **공항 항공편 & 승객 명단**: 20개 노선 항공편(KE081, OZ202 등) 및 35명 등록 승객 특이사항 관리.
- **분실 신고 접수대 & 처리 감사 로그**: 30건의 분실 신고 이력 및 80건의 실시간 위치 갱신/처리 활동 로그 관리.
- **공항 서비스 권한 관리**: 관제 팀장(MANAGER)/스태프(STAFF) 권한 분리 및 긴급 지연 배송 전담 처리.

## ⚠️ 의도적으로 삽입된 8가지 복합 오류 목록

1. **Frontend + Backend 요청 순서 충돌**
   - **설명**: 수하물 상태를 '지연'(DELAYED)으로 변경(3초 지연 완료)한 직후 담당 직원을 변경(0.1초 완료)하면, 담당자 변경 API는 먼저 완료되나 3초 뒤 완료되는 상태 변경 API가 요청 시작 시점의 구 DB 스냅샷(이전 담당자)을 덮어써 저장하여 새로고침 시 수하물 목록의 담당자와 상세 패널의 담당자가 서로 달라집니다.

2. **Backend + JSON DB 상태 충돌**
   - **설명**: 분실 신고 취소 API(0.5초 완료)를 호출한 직후 수하물 위치 갱신 API를 호출(4초 지연 완료)하면, 신고 취소는 성공하지만 늦게 완료된 위치 갱신 요청이 취소된 신고를 다시 LOST_REPORTED 분실신고 상태로 복원시킵니다. 승객 화면에서는 신고 취소, 직원 처리 화면에서는 분실신고 처리중으로 표시됩니다.

3. **Frontend 정렬 인덱스 오류**
   - **설명**: 수하물 목록을 지연시간순/항공편순으로 정렬한 뒤 상세 버튼을 누르면 UI 알림은 클릭한 수하물 태그 번호로 뜨지만, 백엔드 저장 데이터는 정렬 전 원본 배열의 다른 수하물 ID에 연결되는 결함입니다.

4. **통계 집계 불일치**
   - **설명**: 수하물 처리 로그를 삭제(`DELETE /api/processing-logs/:id`) 처리하여 로그 목록에서 소거하더라도, 항공편별 지연 수하물 수(`baggageStats.delayedCount`), 분실 신고율, 직원별 처리량 통계 수치에는 차감되지 않고 계속 잔존합니다.

5. **Network stale response 오류**
   - **설명**: 항공편 필터('KE081' 3초 지연 ➔ 'OZ202' 0.2초 완료)와 수하물 상태 필터를 빠르게 변경 시 오래된 응답(KE081)이 최신 수하물 목록을 덮어써 중앙 목록은 오래된 필터 결과, 오른쪽 처리 요약은 최신 필터 기준 수치로 서로 불일치합니다.

6. **Session + Cache 잔존 오류**
   - **설명**: 직원 A가 수하물 상세를 본 뒤 직원 B로 로그인하면 수하물 목록은 B 담당 기준으로 바뀌지만, 상단 지연 수하물 수 및 최근 승객 상세 캐시(`cachedDelayedBaggage`, `cachedRecentPassenger`)는 A 데이터가 남아 노출됩니다.

7. **Backend 권한 로그 오류**
   - **설명**: 권한 없는 직원(role !== 'MANAGER')이 분실 신고 종결 API(`POST /api/lost-claims/:id/close-unauthorized`)를 호출하면 HTTP 403을 반환하지만, 서버 내부 활동 로그에는 '분실 신고 종결 성공 (LOST CLAIM CLOSED SUCCESSFULLY - 200 OK)'으로 잘못 기록됩니다.

8. **부분 저장 오류**
   - **설명**: 승객 정보 수정 모달/패널에서 연락처, 수령 주소, 요청사항을 동시에 수정하면 백엔드 data.json에는 연락처와 요청사항만 저장되고 수령 주소는 이전 값을 유지하지만, 프론트엔드는 세 항목 모두 수정 성공한 것으로 표시합니다.

## 🧪 테스트 시나리오

1. **Error 1 테스트**: 우측 관제 패널에서 수하물 상태 지연 변경 선택 후 `상태 변경 후 즉시 담당 직원의 변경 (Error 1)` 클릭 ➔ 0.1초 후 담당자 변경 응답 ➔ 3초 후 상태 변경 응답 완료 ➔ 새로고침 시 이전 담당자로 롤백 저장됨을 확인.
2. **Error 2 테스트**: 우측 관제 패널에서 `⚡ 분실 신고 취소 후 위치 갱신 연쇄 실행 (Error 2)` 클릭 ➔ 0.5초 후 신고 취소 응답 ➔ 4초 후 위치 갱신 응답 완료 ➔ 취소된 신고가 LOST_REPORTED 분실신고 상태로 복원됨을 확인.
3. **Error 3 테스트**: 좌측 사이드바에서 `수하물 무게 중량순` 정렬 선택 ➔ 최상단 수하물의 `상세` 클릭 ➔ UI 상단 태그 번호와 우측 관제 패널의 승객명/항공편 정보가 상이함을 확인.
4. **Error 4 테스트**: 중앙 처리 감사 로그 대장에서 `🗑️ 로그 삭제` 클릭 ➔ 대장에서는 삭제되나 대시보드 지연 수하물 통계 수치가 유지됨을 확인.
5. **Error 5 테스트**: 좌측 항공편 필터를 `KE081` 선택 직후 `OZ202` 선택 ➔ 3초 후 늦은 이전 KE081 결과가 최신 OZ202 수하물 목록을 덮어씀을 확인.
6. **Error 6 테스트**: 상단 로그인 담당자를 `김수하 수석`에서 `이분실 전담`으로 전환 ➔ 수하물 목록은 B로 바뀌나 상단 KPI 지연 수하물 건수는 A 데이터로 잔존함을 확인.
7. **Error 7 테스트**: 상단 계정을 일반 스태프 핸들러로 테스트 시 `🔒 권한 없는 일반 직원의 분실 신고 종결 시도` 클릭 ➔ UI/API는 HTTP 403 오류 반환 ➔ 백엔드 콘솔 로그에는 SUCCESS (200 OK)로 잘못 작성됨을 확인.
8. **Error 8 테스트**: 우측 하단 승객 정보 수정 패널에서 수령 주소 포함 입력 후 `승객 정보 저장` 클릭 ➔ 토스트는 성공으로 표시되나 새로고침 시 수령 주소만 수정되지 않았음을 확인.
