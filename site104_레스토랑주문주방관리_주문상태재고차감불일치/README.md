## 📋 정상 기능 요약

- **레스토랑 주문 접수 및 주방 관제 대장**: 45건의 매장 테이블 주문, 접수, 조리중, 조리완료, 서빙완료, 취소, 환불 상태 관제.
- **레스토랑 메뉴 & 식재료 재고 관리**: 30개 메뉴 단가/주재료 정보 및 35개 창고 식재료 보유/안전 재고 관제.
- **재고 차감 내역 & 주방 셰프 팀**: 12명 셰프 팀 배치 및 80건의 식재료 차감 내역/활동 로그 관리.
- **주방 권한 & 매장 구역 관리**: 6개 매장 구역(메인 홀, 루프탑, 프라이빗 룸 등) 및 헤드 셰프(HEAD_CHEF)/스태프(STAFF) 권한 관리.

## ⚠️ 의도적으로 삽입된 8가지 복합 오류 목록

1. **Frontend + Backend 요청 순서 충돌**
   - **설명**: 주문 상태를 '조리중'(COOKING)으로 변경(3초 지연 완료)한 직후 조리 담당자를 변경(0.1초 완료)하면, 담당자 변경 API는 먼저 완료되나 3초 뒤 완료되는 상태 변경 API가 요청 시작 시점의 구 DB 스냅샷(이전 담당자)을 덮어써 저장하여 새로고침 시 주문 칸반보드의 담당자와 주문 상세의 담당자가 서로 달라집니다.

2. **Backend + JSON DB 상태 충돌**
   - **설명**: 주문 취소 API(0.5초 완료)를 호출한 직후 재고 차감 API를 호출(4초 지연 완료)하면, 주문 취소는 성공하지만 늦게 완료된 재고 차감 요청이 취소된 주문을 다시 COOKED 조리완료 상태로 복원시킵니다. 주문 목록에서는 취소됨, 재고 로그에서는 조리완료 주문으로 차감된 것처럼 표시됩니다.

3. **Frontend 정렬 인덱스 오류**
   - **설명**: 주문 목록을 주문금액순/접수시간순으로 정렬한 뒤 상세 버튼을 누르면 UI 알림은 클릭한 주문 번호로 뜨지만, 백엔드 저장 데이터는 정렬 전 원본 배열의 다른 주문 ID에 연결되는 결함입니다.

4. **통계 집계 불일치**
   - **설명**: 재고 차감 로그를 삭제(`DELETE /api/stock-logs/:id`) 처리하여 재고 로그 목록에서 소거하더라도, 메뉴별 판매량, 식재료 사용량, 일일 매출 통계(`opsStats.totalSalesAmount`) 수치에는 차감되지 않고 계속 잔존합니다.

5. **Network stale response 오류**
   - **설명**: 테이블 구역 필터('1층 메인 홀' 3초 지연 ➔ '3층 루프탑' 0.2초 완료)와 주문 상태 필터를 빠르게 변경 시 오래된 응답(1층 메인 홀)이 최신 주문 목록을 덮어써 주문 목록은 오래된 필터 결과, 오른쪽 주방 요약은 최신 필터 기준 수치로 서로 불일치합니다.

6. **Session + Cache 잔존 오류**
   - **설명**: 직원 A가 주문 상세를 본 뒤 직원 B로 로그인하면 주문 목록은 B 담당 기준으로 바뀌지만, 상단 미처리 주문 수 및 최근 주문 상세 캐시(`cachedUnprocessedOrders`, `cachedRecentOrder`)는 A 데이터가 남아 노출됩니다.

7. **Backend 권한 로그 오류**
   - **설명**: 권한 없는 직원(role !== 'HEAD_CHEF')이 식재료 폐기 API(`POST /api/stock/:id/dispose-unauthorized`)를 호출하면 HTTP 403을 반환하지만, 서버 내부 활동 로그에는 '재고 폐기 성공 (STOCK DISPOSAL COMPLETED SUCCESSFULLY - 200 OK)'으로 잘못 기록됩니다.

8. **부분 저장 오류**
   - **설명**: 메뉴 정보 수정 모달/패널에서 메뉴명, 가격, 대표 재료를 동시에 수정하면 백엔드 data.json에는 메뉴명과 대표 재료만 저장되고 가격은 이전 값을 유지하지만, 프론트엔드는 세 항목 모두 수정 성공한 것으로 표시합니다.

## 🧪 테스트 시나리오

1. **Error 1 테스트**: 우측 관제 패널에서 주문 상태 변경 선택 후 `상태 변경 후 즉시 담당 셰프 변경 (Error 1)` 클릭 ➔ 0.1초 후 셰프 변경 응답 ➔ 3초 후 상태 변경 응답 완료 ➔ 새로고침 시 이전 셰프로 롤백 저장됨을 확인.
2. **Error 2 테스트**: 우측 관제 패널에서 `⚡ 주문 취소 처리 후 재고 차감 연쇄 실행 (Error 2)` 클릭 ➔ 0.5초 후 주문 취소 응답 ➔ 4초 후 재고 차감 응답 완료 ➔ 취소된 주문이 COOKED 조리완료 상태로 복원됨을 확인.
3. **Error 3 테스트**: 좌측 사이드바에서 `주문 금액 높은순` 정렬 선택 ➔ 최상단 주문의 `상세` 클릭 ➔ UI 상단 주문ID와 우측 관제 패널의 메뉴명/테이블 정보가 상이함을 확인.
4. **Error 4 테스트**: 중앙 재고 차감 내역 대장에서 `🗑️ 재고 로그 삭제` 클릭 ➔ 대장에서는 삭제되나 일일 매출 수치가 유지됨을 확인.
5. **Error 5 테스트**: 좌측 테이블 구역 필터를 `1층 메인 홀` 선택 직후 `3층 루프탑` 선택 ➔ 3초 후 늦은 이전 1층 메인 홀 결과가 최신 3층 루프탑 주문 목록을 덮어씀을 확인.
6. **Error 6 테스트**: 상단 로그인 셰프를 `김주방 헤드`에서 `이파스타 수셰프`로 전환 ➔ 주문 목록은 B로 바뀌나 상단 KPI 미처리 대기 건수는 A 데이터로 잔존함을 확인.
7. **Error 7 테스트**: 상단 계정을 일반 스태프 셰프로 테스트 시 `🔒 권한 없는 일반 직원의 식재료 폐기 시도` 클릭 ➔ UI/API는 HTTP 403 오류 반환 ➔ 백엔드 콘솔 로그에는 SUCCESS (200 OK)로 잘못 작성됨을 확인.
8. **Error 8 테스트**: 우측 하단 메뉴 정보 수정 패널에서 가격 포함 입력 후 `메뉴 정보 저장` 클릭 ➔ 토스트는 성공으로 표시되나 새로고침 시 가격만 수정되지 않았음을 확인.
